## 审阅范围

- `captures/experiment_20260728_102341_881_30c34f`

## 当前同步设计

当前实现属于“统一生命周期和统一逻辑时间基准”，而不是硬件级逐样本同步：

1. 所有配置设备先连接或打开端口，全部报告 ready 后才打开共享采集门。
2. Start、Pause、Resume、Stop 对所有活动 Source 统一生效。
3. 所有托管 Source 共享 `CaptureClock`，Pause 期间逻辑时间不增加。
4. 每台 W2 的第一包按共享时钟锚定；第一包之后根据配置的 1000 Hz 独立生成
   连续 `time_s`。
5. BWT901 没有可用的设备时间戳，使用共享时钟下的主机通知接收时间。
6. CaptureStore 和 CSV 按 Stream 独立保存，不要求不同设备行数相同。

当前保证：

- 所有必要设备 ready 后才开始；
- 统一启停与 Pause/Resume；
- 共享、排除 Pause 的逻辑时间原点；
- 每个 Stream 内时间单调；
- 任一必要 Worker 出错时整次采集 fail-fast。

当前不保证：

- 命令在所有物理设备上同一瞬间执行；
- 第一硬件样本完全同刻；
- 多台 W2 使用同一个采样时钟；
- 各 Stream 行数相同；
- W2 完整帧丢失一定能被检测；
- 跨设备毫秒级相位同步。

## 对行数差异的判断

按独立 Stream 保存实际收到的数据、不补零、不强制截断，是刻意的设计。这样
不会为了制造等长矩阵而伪造样本或丢弃原始数据。

但 1.1–1.4 秒的末端差异不是期望制造的结果，而是独立设备时钟、启停响应、
串口调度及收到帧数差异的外在表现。当前时间戳只在第一包使用共享时钟，之后
严格按配置频率递增，因此不会自动修正长期漂移。

## 后处理要求

不能直接按 CSV 行号把多台 W2 拼成通道矩阵。最低要求是：

1. 以 `time_s` 为依据；
2. 取所有必需 Stream 的公共时间区间；
3. 在不覆盖原始 CSV 的前提下，按分析目标生成统一时间网格的派生数据；
4. 明确记录重采样频率、插值方法、公共区间和被排除的数据范围。

当前数据适合多数按时间窗提取特征或动作分类的任务。若研究跨通道相位、相干性、
精确起始潜伏期或毫秒级 EMG–IMU 融合，现有软件同步不足。

两次实验包含 IMU 时的公共覆盖区间约为：

- `102341`：0.427143–577.747960 s
- `103452`：0.410219–435.699250 s

## 本次已修正的问题

第二次实验 metadata 中 W2 的 `observed_rate_hz` 约为 15.8 包/s，该值不可信。
原实现每次 Resume 会重置活动开始时刻，但累计帧数不会清零，造成累计分子除以
最后一段活动时长。

修正后，W2 Worker 会累计多个活动区间的总时长，累计帧数与累计活动时长使用
一致口径。该修改只影响健康状态的速率显示，不改变采集、时间戳或保存数据。

## 后续建议

按优先级建议：

1. 保持当前独立 raw CSV，不补零、不覆盖、不静默截断。
2. 在 metadata 中补充每台设备首末接收时间、包数、估计有效采样率和漂移诊断。
3. 如后处理频繁需要多通道矩阵，提供单独的“公共区间 + 统一网格”派生导出工具，
   并保留完整参数记录。
4. 若实验要求严格毫秒级同步，应确认 W2 硬件是否支持共享触发、共享时钟、帧计数
   或可观测的共同同步事件；纯软件启动屏障无法替代硬件同步。
